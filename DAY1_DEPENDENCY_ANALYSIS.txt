DETAILED VIOLATION ANALYSIS
===============================================

VIOLATION #1: plugin_manager.py → capability_registry (register_provider)
  File: core/plugin_manager.py
  Line: ~145-150 (in load_plugin method)
  Code: 
    await reg.register_provider(
        plugin_name,
        cap_id,
        provider_type=provider_type,
        remote_config=metadata.remote_config,
        plugin_privilege=plugin_privilege
    )
  
  Pattern: DIRECT CALL (tightly coupled)
  Alternative: Event-based "plugin.loaded(name, metadata)" → capability_registry listens
  
  Why It Matters: 
    - PluginManager shouldn't know capability_registry implementation
    - Different plugins might use different capability frameworks
    - Event pattern allows swapping capability providers
  
  Refactoring Priority: PHASE 4 (long-term, after split)
  Risk of Changing Now: MEDIUM (affects plugin startup sequence)
  Recommendation: Leave as-is during split, refactor later via event-bus


VIOLATION #2: plugin_manager.py → capability_registry (unregister_plugin)
  File: core/plugin_manager.py
  Line: ~280-285 (in unload_plugin method)
  Code:
    cap_reg.unregister_plugin(plugin_name)
  
  Pattern: DIRECT CALL (tightly coupled)
  Alternative: Event-based "plugin.unloading(name)" → capability_registry listens
  
  Why It Matters: Same reasons as Violation #1
  
  Refactoring Priority: PHASE 4 (long-term)
  Risk of Changing Now: MEDIUM (affects plugin shutdown sequence)
  Recommendation: Leave as-is during split


VIOLATION #3: plugin_manager.py → operations (unregister_handler)
  File: core/plugin_manager.py
  Line: ~282 (in unload_plugin method)
  Code:
    ops_mgr.unregister_handler(cap_id)
  
  Pattern: DIRECT CALL (tightly coupled)
  Alternative: Event-based "plugin.unloading(name)" → operations listens
  
  Why It Matters: 
    - PluginManager shouldn't orchestrate operations registry
    - Different operations systems might have different handlers
    - Event pattern allows decoupling
  
  Refactoring Priority: PHASE 4 (long-term)
  Risk of Changing Now: MEDIUM (affects plugin shutdown)
  
  Recommendation: Leave as-is during split


VIOLATION #4: operations.py → capability_registry._lock (direct lock access)
  File: core/operations.py
  Line: ~545-548 (in execute method)
  Code:
    with cap_reg._lock:
        all_providers = cap_reg.get_all_providers_for_capability(operation.type)
  
  Pattern: ENCAPSULATION VIOLATION (accessing _lock private attribute)
  Problem: 
    - _lock is implementation detail of capability_registry
    - Operations shouldn't assume capability_registry uses threading.RLock
    - If capability_registry changes locking strategy, operations breaks
  
  Fix Required:
    1. Add method to capability_registry:
       def atomic_get_providers_for_capability(self, cap_name: str) -> Tuple[List[ProviderMetadata], Dict]:
           with self._lock:
               all_providers = ...
               return all_providers, snapshot_dict
    
    2. Use in operations.py:
       all_providers, provider_snapshot = cap_reg.atomic_get_providers_for_capability(operation.type)
  
  Refactoring Priority: SHORT-TERM (should fix before split)
  Risk of Changing Now: LOW (isolated to capability_registry)
  Impact: ~ 10 LOC change in capability_registry
  
  Recommendation: FIX THIS IN NEXT PHASE (pre-split improvement)

def atomic_get_providers_for_capability(
    self, 
    cap_name: str
) -> List[Dict[str, Any]]:
    """Thread-safe snapshot of providers for capability."""

        providers = self.get_all_providers_for_capability(cap_name)
