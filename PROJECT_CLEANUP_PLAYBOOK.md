# Project Cleanup Playbook

## Цель
Сделать проект проще и предсказуемее:
- меньше legacy-слоёв и дублирования
- меньше случайных импортов из устаревших путей
- понятная карта ответственности по пакетам
- стабильный и быстрый регресс

## Принцип
Сначала стабилизируем поведение, потом упрощаем структуру. Не смешивать рефакторинг архитектуры, фиксы багов и изменение фич в одном PR.

## Что сейчас мешает простоте
- В core одновременно живут канонические пакеты и backward-compat wrappers.
- Много массовых импорт-миграций в одном диффе затрудняют ревью.
- Есть пакетные рефакторинги, которые выглядят как усложнение, если не завершить последнюю фазу (удаление обёрток).

## Финальное состояние (Definition of Done)
1. В production-коде нет импортов из legacy-wrapper файлов.
2. Legacy-wrapper файлы либо удалены, либо оставлены только там, где это критично для внешних интеграций.
3. Все архитектурные слои отражены в 1 короткой карте (README + roadmap).
4. Рефакторинг разбит на маленькие PR (до 20 файлов/PR, если возможно).
5. Полный pytest зелёный.

## Пошаговый план

### Фаза 0. Стабилизация перед уборкой
- Зафиксировать baseline: текущий зелёный прогон тестов.
- Не добавлять новые migration-изменения, пока не разобран существующий дифф.
- Подготовить 1 технический PR только для cleanup-процесса.

Команды:
```bash
pytest -q
rg "from core\.(service_registry|http_registry|module_manager|capability_registry|dependency_resolver|policy_engine) import" -g"*.py"
```

### Фаза 1. Инвентаризация и группировка изменений
Разделить изменения на 4 независимые группы:
1. Critical fixes (например, баги, как в plugin_isolation докстроке).
2. Import-only migrations (без изменения логики).
3. Архитектурные переносы файлов/пакетов.
4. Тесты и документация.

Результат:
- Каждая группа уходит в отдельный PR.
- Легко откатывать и ревьюить.

### Фаза 2. Canonical imports only
Для production-кода оставить только канонические импорты:
- core.service
- core.http
- core.module
- core.capability
- core.dependency
- core.policy
- core.storage_layer

Запретить новые legacy-импорты в CI (grep-check).

Пример CI-проверки:
```bash
if rg -n "from core\.(service_registry|http_registry|module_manager|capability_registry|dependency_resolver|policy_engine) import" core modules main.py; then
  echo "Legacy import detected"; exit 1
fi
```

### Фаза 3. Удаление или минимизация wrappers
Правило:
- Если wrapper больше 20-30 строк и содержит логику, а не re-export, это кандидат на удаление/упрощение.

Порядок:
1. Оставить только thin re-export wrappers.
2. Убрать deprecated warnings из hot-path, если они шумят в тестах.
3. После 1-2 релизных циклов удалить wrappers полностью.

### Фаза 4. Упрощение структуры core
Цель: уменьшить когнитивную нагрузку.

Рекомендуемая схема:
- core/runtime
- core/service
- core/http
- core/capability
- core/dependency
- core/security
- core/storage_layer
- core/shared (контексты, логгер-хелперы, утилиты)

Правило размера:
- Если файл > 350-400 строк, делить по ответственности.
- Если пакет содержит только 1 файл без перспектив роста, не дробить дальше.

### Фаза 5. Документация, которая реально помогает
Обновить только 3 документа:
1. README: как запустить и как тестировать.
2. ARCHITECTURE.md: карта слоёв и зависимости.
3. MIGRATION.md: old path -> new path.

Убрать устаревшие отчёты-фантомы, дублирующие roadmap.

### Фаза 6. Автоматизация чистоты
Добавить в CI:
- import guard (legacy path ban)
- ruff/pyright/pytest минимальный набор
- проверка что нет случайных debug default, раскрывающих данные

## Рекомендуемый порядок PR
1. PR-1: критические фиксы + мелкие артефакты (без архитектуры).
2. PR-2: import-only migration (без изменения поведения).
3. PR-3: wrappers cleanup (thin wrappers).
4. PR-4: удаление wrappers + финальная docs cleanup.

## Правила для каждого cleanup PR
- Один смысл PR.
- Не смешивать plugins/core/modules, если не обязательно.
- В описании PR: список затронутых пакетов + риск + чек тестов.

## Быстрый чеклист перед merge
- [ ] Нет новых legacy-импортов.
- [ ] Нет случайных артефактов в докстроках/комментариях.
- [ ] pytest зелёный.
- [ ] Изменения читаемы как отдельный раздел миграции.
- [ ] Обновлён минимум 1 архитектурный документ.

## Антипаттерны, которых избегать
- "Большой рефакторинг всего сразу".
- Изменения API вместе с переносом файлов.
- Смешивание форматирования/переименований/логики в одном коммите.
- Вечные wrappers без дедлайна на удаление.

## Прямо сейчас (короткий next step)
1. Зафиксировать отдельным коммитом критические артефакты и мелкие фиксы.
2. Отдельно подготовить import-only PR в core+modules.
3. После зелёного регресса сделать PR на thinning/removal wrappers.
