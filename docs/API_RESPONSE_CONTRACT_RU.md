## Контракт HTTP-ответов (Core Runtime Service)

Цель: **один предсказуемый стиль ответов** для всех API ручек и сервисов.

### Общий принцип

- **Успех**: канонический ответ — `{"ok": true, "result": <payload>}`.
- **Ошибки**: код HTTP **не 200**, тело ошибки — `{"ok": false, "error": "...", "code": "..."}` (или FastAPI `{"detail": "..."}` там, где это уместно).

### Успешные ответы

- Для любого метода (`GET/POST/PUT/PATCH/DELETE`):
  - если сервис/handler вернул `{"ok": ...}` — payload сохраняется **как есть** (backward compatible);
  - иначе успешный результат нормализуется в `{"ok": true, "result": ...}`.

### Ошибки

- Ошибка должна быть отражена **HTTP кодом**:
  - `400` — невалидный запрос
  - `401` — неавторизован
  - `403` — недостаточно прав
  - `404` — не найдено
  - `409` — конфликт/гонка
  - `429` — rate limit (в dev можно отключать)
  - `5xx` — ошибки сервера

- Тело ошибки:
  - предпочтительно `{ "ok": false, "error": "..." , "code": "..." }` (для единообразия с клиентами),
  - либо стандартный FastAPI `{ "detail": "..." }`.
  - Главное: **не прятать ошибки под HTTP 200**.

### Совместимость / миграции

- Старые сервисы, которые уже возвращают `{"ok": ...}` — допустимы, но:
  - ошибка всё равно должна быть выражена **HTTP статусом**.
  - если сервис возвращает `{"ok": false, ...}`, то `modules/api/route_binding.py` может выставить `response.status_code` по полю `status` (backward compatible), но целевой путь — **исключения/HTTP статусы**, а не поле `status` в JSON.

### Реализация в коде

- В `modules/api/route_binding.py`:
  - если сервис вернул dict с ключом `"ok"` — ответ сохраняется как есть (backward compatible),
  - иначе успешный ответ заворачивается в `{"ok": true, "result": ...}`.
  - HTTP статус выставляется через `response.status_code` (и только в рамках backward-compat допускается `status` поле в dict-ответе).
